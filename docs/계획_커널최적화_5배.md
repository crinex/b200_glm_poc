# 커널 최적화 계획 — "5배" 를 물리 예산으로 분해 (2026-09-02)

## 1. decode 1스텝 예산 (conc128, MTP1 → 스텝당 256 토큰, TP8, B200 HBM 8 TB/s)

config.json 실값: 78층(dense 3 + MoE 75), hidden 6144, expert 256 × top-8 + shared 1, moe_inter 2048,
MLA kv_lora 512 + rope 64, DSA index_topk 2048, 인덕서 full 21층(IndexShare), MTP 1층, vocab 154,880.
가중치 합 742GB(계산) = 로그 실측(92.7GiB×8) → 모델 검증됨.

| 항목 | ms/step | 비고 |
|---|---|---|
| MoE+attn 가중치 읽기 (92.8GB/GPU) | **11.6** | 256토큰×8 = 2,048 선택 → expert 99.97% 접촉. 전 가중치 매 스텝 읽음 |
| sparse KV 읽기 (쿼리당 2048토큰×576B×78층) | 2.9 | **TP8 은 8장이 같은 KV 를 중복으로 읽음** → DP-attn 이면 0.4 |
| 인덕서 K cache (ctx 9.2k × 128B × 21층) | 0.4 | |
| 컴퓨트 (active ~40B × 256토큰) | 1.1 | 메모리와 겹침 — **컴퓨트 바운드 아님** |
| all-reduce 156회 (3.1MB, ~20µs) | 3.1 | 순차 |
| **루프라인 바닥** | **≈18** | |
| **실측** (TPOT 55ms × accept 1.75) | **≈96** | |
| 실측/바닥 | **5.3×** | |

→ **"5배" = 루프라인에 거의 도달하라는 뜻.** 커널만으로는 안 되고, 바닥 자체를 낮추는 시스템 변경과 곱해야 한다.
- NVFP4 experts(가중치 ~절반) + DP-attn(KV 중복 제거) → 바닥 ≈ **10ms**
- MTP accept 1.75 → 3.0 이면 같은 스텝 시간에 토큰 1.7×

## 2. 실측 96ms 중 ~78ms 오버헤드는 어디에? — 가설 (프로파일로 확정 필요)

| 후보 | 추정 | 왜 |
|---|---|---|
| MoE grouped GEMM 대역폭 효율 | 25~35 ms | TP8 이라 expert 당 M≈8행, 가중치 조각 4.7MB. 타일 M=64/128 낭비, 256 expert 순회 스케줄. trtllm-gen 이 SM 140 을 잡고도 8TB/s 의 30~50% 로 추정 |
| DSA 인덕서 logits + top-k(2048 of 9.2k) × 21층 × 256쿼리 | 10~20 ms | TRT-LLM: torch.topk 대비 커스텀 7.4×, 인덕서가 저지연 e2e 의 25~40% |
| sparse gather attention (2048개 랜덤 576B 행 gather) | 5~10 ms | FlashMLA sparse decode B200 350 TFLOPS "미최적화" 표기. 비정렬 gather 대역폭 효율 낮음 |
| MTP draft 패스 (MTP층 + lm_head 154,880×6144 + 별도 AR·샘플링 체인) | 5~10 ms | 스텝마다 소형 forward 1회 추가, 커널 수는 본체 1층분 + lm_head |
| all-reduce + RMSNorm 미퓨전, 소메시지 지연 | 4~6 ms | 156회 순차. 8×B200 symm-mem AR 비효율 이슈 #33459 |
| 스케줄러/CPU/그래프 경계 (FULL_AND_PIECEWISE 의 piecewise 구간, rejection sampling, 블록테이블 갱신) | 5~10 ms | async scheduling 켜져 있어도 piecewise 경계마다 launch 갭 |
| 소형 커널 (RMSNorm, RoPE, quant, permute/unpermute, SwiGLU, router softmax/topk) | 5~10 ms | 층당 ~25개 × 78 = 2,000개, 각 3~5µs |

## 4. 곱셈 스택 — 현실적 시나리오

| 단계 | 스텝 시간 | 토큰/스텝 | Output tok/s (conc128) | 배수 |
|---|---|---|---|---|
| 현재 | 96 ms | 1.75 × 128 | 2,250 | 1.0 |
| + MTP 3~5 (accept 1.75→2.7, 드래프트 비용 +8ms) | 104 | 2.7 × 128 | 3,320 | 1.5 |
| + DP-attn/EP8 (KV 중복 제거, AR 절반) + K1 MoE 재편 | 75 | 〃 | 4,600 | 2.0 |
| + K2 인덕서 + K4/K6/K7 퓨전 | 50 | 〃 | 6,900 | 3.1 |
| + NVFP4 experts (바닥 −5ms, 실효 −10) | 40 | 〃 | 8,600 | **3.8** |
| + K3 sparse attn + conc 256 (KV 여유 생김) | 35 | 2.7 × 256 | ~15,000 이론 / 현실 ~10,000 | **4.5~6** |

정직한 판독:
- **커널만(K1~K7)으로는 ~2× 가 상한** (96 → 50ms). 5.3× 갭 전부를 커널이 먹지는 못함.
- **5×는 커널 2× × 시스템 2.5×(MTP·DP/EP·NVFP4·conc↑)의 곱** 으로만 도달 가능. 이 중 시스템 쪽은 메인 실험 축과 겹친다.
- 순서는 **측정 → 큰 덩어리(K1, K2) → 퓨전 묶음(K4~K7) → K3**.

## 6. 도구 스택 결정
- **Triton 3.7** (K2, K5, K6): tcgen05 불필요한 메모리·정수 커널. `torch.library.custom_op` + `register_fake` 로 vLLM 삽입, CUDA graph 호환 확인
- **CuTe DSL / CUTLASS 4** (K1, K3): FlashInfer 가 vLLM sm_100 커널을 이 스택으로 JIT → 포크·튠이 자연스러움
- **DeepGEMM 패치** (K1 대안): MegaMoE 경로가 우리가 원하는 퓨전 그 자체
- Mojo: 커널 소스(sparse MLA decode, bitonic top-k, NVFP4 grouped matmul)는 **설계 참조**로만. vLLM 플러그인 경로는 experimental (조사_서빙프레임워크_커널최적화.md §3-1)
