## 0. 먼저 바로잡을 것 — "우리는 프론티어 대비 4~6배 뒤처졌다"는 단위 착오

한 조사 축이 "공개 프론티어 1,300~1,750 tok/s/GPU vs 우리 281 tok/s/GPU" 라고 보고했지만, **InferenceX 의 tok/s/GPU 는 입력+출력 합산**이다 [확인됨, r-sglang 검증]. 우리 수치를 같은 단위로 바꾸면:

| | conc | Output tok/s (노드) | Input+Output tok/s/GPU |
|---|---|---|---|
| **우리 vLLM 0.28 TP8 MTP1** (서버 D/E) | 128 | 2,193~2,251 | **≈2,470** |
| InferenceX GLM-5 FP8 B200 TP8 SGLang v0.5.12 + MTP3 | 128 | ≈1,764 [확인됨] | 1,947 [확인됨] |
| InferenceX GLM-5 **NVFP4** B200 **TP4** SGLang + MTP | 128 | — | 4,116 [확인됨] |
| Lambda GLM-5.2-FP8 HGX B200 (8k/2k, conc32, spec 없음) | 32 | SGLang 1,454 / vLLM 1,264 [확인됨] | — |

→ **FP8 TP8 에서 우리 vLLM 결과는 이미 공개 SGLang 수치보다 높다.** 격차가 실제로 큰 곳은 **NVFP4 (~1.7×)** 한 군데다. "SGLang 으로 옮기면 5배" 같은 기대는 하지 말 것.
(TRT-LLM DSv3.2 블로그의 1,077 tok/s/GPU 도 단위 미확정 — conc256 × 11.3 tok/s/user = 노드 출력 2,893 이므로 우리 대비 +30% 수준으로 읽는 게 안전 [추정].)

## 1. 네 축이 수렴하는 결론

네 조사가 서로 독립적으로 같은 세 가지를 최우선으로 짚었다.

| 순위 | 레버 | 왜 우리 병목에 맞나 | 근거 |
|---|---|---|---|
| **1** | **MTP 스텝 확대 (1 → 3~5)** | decode-bound. 우리 spec=1 은 accept 1.75. GLM-5.2 는 MTP 7단계로 학습, 공식 평균 수락 5.47. Z.ai vLLM B200 레시피가 `num_speculative_tokens 5`, Dynamo 레시피 3(accept 2.69), SGLang 쿡북 steps 5/draft 6 | [확인됨] 4축 전부 |
| **2** | **NVFP4 체크포인트 (`nvidia/GLM-5.2-NVFP4`)** | MoE 가중치 대역폭이 decode 시간의 주범 + KV 용량 한계(상주 ~150). 전문가만 4bit, attention·shared·MTP 는 FP8/BF16 유지. 메모리 ~740→~460GB → KV 슬롯 2배+, TP4 적재 가능 | [확인됨] 존재·정확도(GPQA 89.5→89.4). 품질 반론 1건(agentic CoT 붕괴, umans.ai) |
| **3** | **DP-attention + EP8** (KV 중복 제거) | TP8 MLA 는 KV 가 8장에 **중복** 저장. DP8 이면 GPU 마다 자기 요청 KV 만 → 상주 한계 이론상 최대 8×. 오늘 실측 TP2·DP4·EP8 이 **정확히 이 방향**(KV 985k×4 = TP8 의 2.7배) | [확인됨] 원리 / [추정] 8k/1k 단일노드 이득 크기 — 공개 수치 없음 |

이 세 가지는 **vLLM 안에서도 가능**하다. 즉 "프레임워크 교체"는 3순위 이후의 질문이다.

### 오늘 spec=2 실측(−19% @conc32, +6.6% @conc128)과의 충돌
공개 수치는 스텝 3~5 에서 이득인데 우리 spec=2 는 저conc 에서 손해였다. 가능한 원인 [추정]:
- vLLM MTP 수락률 버그 — Z.ai 레시피가 **PR #45895 수정 포함 버전** 을 요구. 0.28.0 에 포함됐는지 확인 필요
- vLLM #28312 (k=2 IMA) 우회로 PIECEWISE cudagraph 필요
- IndexShare(4레이어당 인덱서 1개) 를 vLLM 이 MTP draft 에서 재사용하는지(SGLang 은 "IndexShare MTP 로 드래프트 비용 1.9×↓")
→ **메인 실험 세션에 전달할 것**: `num_speculative_tokens 3, 5` 스윕 + accept length 로그 + vLLM 버전의 #45895 포함 여부.

## 3. 커널 작성 — 언어 선택과 첫 타깃

### 3-1. Mojo 는 "MAX 를 통째로 쓸 때만"
- Mojo 자산은 좋다: sm_100 tcgen05/TMEM/TMA/2-CTA 프리미티브, BF16 GEMM SOTA 85%, 그리고 **우리 후보 커널 5종이 오픈소스 Mojo 로 이미 존재** (blockwise FP8 matmul, NVFP4 grouped matmul, sparse MLA decode, DSA indexer bitonic top-k, EP dispatch/combine, GEMM+SwiGLU) [확인됨]. Mojo 1.0 은 Apache 2.0.
- 그러나 **vLLM 에 붙이는 길이 약하다**: `max.experimental.torch.CustomOpLibrary` 가 experimental, 동적 shape 재컴파일·스칼라 미지원 이력, CUDA graph 호환 문서 없음 [확인됨]. decode 경로는 CUDA graph 필수라 MAX 런타임 우회해 PTX/cubin 직접 로드가 필요할 가능성 [추정] → PoC 만 +1주.
- **활용법**: Mojo 커널 소스를 **설계 참조**로 읽고, 구현은 아래 언어로.

### 3-2. 현실적 언어 순위 (소규모 팀, 수 주)
**Triton/Gluon ≥ CuTe DSL(Python) > TileLang > ThunderKittens > Mojo(플러그인 용도)**

| 도구 | sm_100 상태 [확인됨] | 용도 |
|---|---|---|
| Triton 3.7 Gluon | tcgen05 mma(+block-scaled), TMEM, TMA multicast, 2CTA. 코어 Triton 은 tcgen05 제한적 | 메모리바운드·정수 로직 커널 (indexer, router, sampling) |
| CUTLASS 4 / CuTe DSL | sm_100a block-scaled grouped GEMM 예제. **FlashInfer 가 vLLM 기본 sm_100 커널을 CuTe DSL 로 JIT 배포** → vLLM 0.28 과 동일 스택 | attention·GEMM 계열 (기존 FlashInfer 커널 포크) |
| DeepGEMM | SM100 grouped GEMM, UE8M0, MegaMoE(dispatch+GEMM+SwiGLU+combine 퓨전), 인덱서 MQA logits — vLLM 이 인덕서 커널을 여기서 사용 | 패치 대상 |
| FA4 / ThunderKittens 2.0 / TileLang / cuTile | 존재하나 MLA/DSA decode 경로 없음 또는 예제 미성숙 | 참고 |

### 3-3. 첫 커널 = DSA indexer + top-k gather 퓨전 (Triton)
- 왜 이것: DSA 모델은 attention 1스텝 커널 시간이 MLA 의 **2.7배** [확인됨 vLLM GB300 블로그]. 인덕서 logits + top-k(2048) 가 매 레이어 고정 비용. TRT-LLM 은 radix-select top-k 로 torch.topk 대비 7.41×, indexer 최적화로 e2e 25~40%(저지연) [확인됨]. MLSys 2026 FlashInfer 콘테스트 DSA 트랙 **1위가 Triton 구현(37×)** — 참조 코드 공개.
- tcgen05 불필요(메모리바운드·정렬) → Triton 으로 충분, `torch.library.custom_op` 로 `vllm/v1/attention/backends/mla/indexer.py` 에 env flag 교체.
- **PoC 7~10 영업일**: 베이스라인 프로파일(0.5d) → 커널(3~5d) → 등록·정확도(1d) → CUDA graph 검증(1d) → 벤치(1d). 목표 레이어당 인덕서 ≥3×, e2e TPOT −5~10% [추정].
- **커널 없는 대체재 먼저**: vLLM `--hf-overrides '{"use_index_cache":true,"index_topk_freq":4}'` (레이어 간 top-k 재사용) — 정확도 검증 필수.

### 3-4. 그 외 후보 커널 (후순위)
| 커널 | 언어 | 근거 |
|---|---|---|
| MoE router+topk+permute 퓨전 | Triton | 소형 GEMM+softmax+scatter. vLLM 에 소배치 router GEMM 이미 유입 |
| Grouped FP8 GEMM + SwiGLU epilogue | CuTe DSL 또는 DeepGEMM 패치 | MoE 가 SM 140/148 독점. DeepGEMM MegaMoE 가 이미 이 방향 |
| Sparse MLA decode | CuTe DSL (FlashInfer 포크) | FlashMLA B200 350 TFLOPS "미최적화" 표기. 기대 ±5% [추정] |
| 인덕서 K 저장/blockwise FP8 quant 퓨전 | Triton | TRT-LLM: op 32~64%, e2e +3.5~13.4% |
| Sampling 퓨전 | Triton | 단순 |

## 5. 실행 로드맵 (이 세션 담당 축)

**Phase A — 정밀도 결정 (2일)**
1. `nvidia/GLM-5.2-NVFP4` 다운로드 (`VLLM_USE_FLASHINFER_MOE_FP4=1`, KV fp8 유지, TP8 → TP4 도 시험)
2. 동일 gen8k 8k/1k 스윕 → FP8 대비 tok/s, KV 슬롯 수
3. **품질 게이트**: 우리 워크로드에 가까운 롱호라이즌/툴콜 평가 (umans.ai 반론 재현 여부). 통과 못 하면 FP8 유지

**Phase B — 프레임워크 A/B (각 1일, 같은 서버·같은 워크로드)**
1. SGLang Step A (TP8+MTP3) → Step B (DP8+EP8+DeepEP) → Step C (MTP5). `_research/04_sglang_raw.md §6` 명령 그대로
2. TRT-LLM FP8: TP8/EP8, DEEPGEMM, MTP1, ADP on/off. 툴콜 스모크 먼저
3. MAX: `max serve zai-org/GLM-5.2-FP8` TP8 1회 (대조군)
- 판정 기준: 노이즈 바닥 ±5% 초과 + conc 128/256 기준 + 지문 동봉 (기존 방법론 유지)

**Phase C — 커널 PoC (7~10일, Phase A/B 와 병행 가능)**
- DSA indexer+top-k 퓨전 (Triton), §3-3 순서. 먼저 IndexCache 로 상한 감 잡기

**Phase D — 조합**
- 승자 정밀도 × 승자 프레임워크 × MTP 스텝 × DP/EP 를 한 서버에서 재대조
