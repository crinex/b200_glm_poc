# 조사 — 아직 안 건드린 고효과 옵션 (DP attention 처럼 놓친 것 찾기)

DP attention(TP2·DP4·EP8)이 conc=256 에서 +47% 를 낸 것처럼, 계산만으로
"안 될 것"이라 넘겼다가 실측이 뒤집을 수 있는 후보를 **vLLM 0.28.0 소스에서
직접 확인**해 정리한다 (285개 옵션 전수 스캔). NVFP4 는 요청대로 제외.

각 항목: [소스확인] = argparse/config 원문으로 존재·조건 확인 / [가설] = 기대는
논리적이나 실측 필요.

---

## ★ 1순위 — DCP (Decode Context Parallel) [소스확인]

`--decode-context-parallel-size N`

### 왜 큰가
config 원문: *"Number of ranks that shard the decode KV cache.
**DCP does not expand the process world size. Without PCP, DCP reuses TP ranks.**"*

**이게 핵심이다.** DCP 는 world size 를 안 늘리고 TP 랭크를 재사용해서
**decode KV cache 를 시퀀스 축으로 분할**한다. 즉 **DP 를 쓰지 않고도
(TP=8 유지) KV cache 유효 용량을 늘릴 수 있는 유일한 레버**일 수 있다.

- DP attention 은 KV 를 2.67배로 늘렸지만 저conc 를 −33% 희생했다
  (요청이 rank 로 흩어져 rank당 TP=2 라 느림)
- DCP 는 TP=8 을 유지하므로 **저conc 손실 없이 KV 만 늘릴 가능성**이 있다
  → DP attention 의 장점(KV↑)만 취하고 단점(저conc↓)은 피하는 시나리오

### 확인된 것 / 미확인
- MLA(`mla_attention.py`)에 DCP 코드 경로 존재 — 우리 모델(MLA) 지원 가능성
- `--dcp-comm-backend {ag_rs, a2a}` 로 통신 방식 선택
- **미확인**: GLM sparse MLA(DEEPSEEK_V32_INDEXER)에서 실제 기동되는지.
  기동 즉시 판정됨 (리스크 낮음)

### 실험
```
dcp2     NO_EP=1 SPEC_TOKENS=1 EXTRA_ARGS="--decode-context-parallel-size 2"
dcp4     NO_EP=1 SPEC_TOKENS=1 EXTRA_ARGS="--decode-context-parallel-size 4"
```
판정: 기동 로그 `GPU KV cache size` 가 1.48M 대비 늘고, 저conc 가 안 죽으면
**DP attention 상위 호환**. conc 4~256 full sweep 필요.

## ★ 2순위 — DBO (Dual Batch Overlap) [소스확인]

`--enable-dbo` (+ `--dbo-decode-token-threshold`, `--dbo-prefill-token-threshold`)

### 왜 큰가
config 원문: *"Enable dual batch overlap for the model executor."*
배치를 2개 마이크로배치로 쪼개 **한쪽이 통신(all-reduce/all-to-all)하는 동안
다른쪽이 계산**하게 겹친다. TP=8 은 decode 스텝마다 all-reduce 를 하고,
EP 구성은 all-to-all 을 한다 — **통신을 계산 뒤에 숨기면** 그만큼 빨라진다.

우리 실측에서 EP8 이 −5% 였던 게 all-to-all 통신 비용 때문이었는데,
DBO 는 정확히 그 비용을 겹쳐 없애는 기법이다. **EP + DBO 조합이 EP 단독의
손실을 상쇄할 가능성.**

### 발동 조건 (소스)
```
dbo_decode_token_threshold = 32   # 배치 토큰 > 32 여야 decode DBO 발동
dbo_prefill_token_threshold = 512
```
- 우리 워크로드는 ISL 8,200 이라 prefill 은 항상 임계 초과.
  decode 도 conc 크면 초과 → **고conc 에서 발동**
- `gpu_ubatch_wrapper.py` 로 마이크로배치 래핑 확인됨

### 실험
```
dbo         NO_EP=1 SPEC_TOKENS=1 EXTRA_ARGS="--enable-dbo"
dp4_dbo     TP=2 DP=4 SPEC_TOKENS=1 EXTRA_ARGS="--enable-dbo"   # EP8+DBO
```

## ★ 3순위 — all2all 백엔드 (MoE 통신) [소스확인]

`--all2all-backend {allgather_reducescatter(기본), deepep_high_throughput,
deepep_low_latency, deepep_v2, flashinfer_all2allv, flashinfer_nvlink_one_sided}`

### 왜 큰가
EP 구성의 MoE dispatch/combine 통신을 담당. 기본
`allgather_reducescatter` 는 범용이고, **`deepep_*` 는 DeepSeek 계열 MoE 에
특화된 고속 커널**이다. `flashinfer_nvlink_one_sided` 는 단일 노드 NVLink
전용 최적화로 보인다.

우리 EP8 / TP2·DP4·EP8 의 all-to-all 비용을 직접 낮추는 후보.
`deepep_low_latency` 는 저conc, `deepep_high_throughput` 는 고conc 겨냥.

### 주의
deepep 은 별도 커널 라이브러리가 필요할 수 있다 (설치 안 됐으면 기동 실패
→ 즉시 판정). `flashinfer_nvlink_one_sided` 는 flashinfer 내장이라 가능성 높음.

### 실험 (EP 켠 구성 위에서만 의미)
```
dp4_a2a_ll   TP=2 DP=4 SPEC_TOKENS=1 EXTRA_ARGS="--all2all-backend deepep_low_latency"
dp4_a2a_ht   TP=2 DP=4 SPEC_TOKENS=1 EXTRA_ARGS="--all2all-backend deepep_high_throughput"
dp4_a2a_fi   TP=2 DP=4 SPEC_TOKENS=1 EXTRA_ARGS="--all2all-backend flashinfer_nvlink_one_sided"
```

## 중간순위 — 확인은 됐으나 기대 중간

### 4. `--scheduler-reserve-full-isl` (기본 True) [소스확인]
KV 를 요청의 full ISL 만큼 예약하는 보수적 정책. **끄면**(`--no-scheduler-reserve-full-isl`)
admission 이 공격적이 되어 상주 요청이 늘 수 있다 → 고conc 처리량↑ 가능.
단 OOM/선점 위험. 저비용 실험.
```
noreserve   NO_EP=1 SPEC_TOKENS=1 EXTRA_ARGS="--no-scheduler-reserve-full-isl"
```

### 5. `--expert-placement-strategy round_robin` (기본 linear) [소스확인]
EP 부하 불균형(우리가 EP8 −5% 원인으로 지목)을 완화. 인기 전문가를
GPU 에 고르게 흩는다. EP 구성에서만 의미.
```
dp4_rr      TP=2 DP=4 SPEC_TOKENS=1 EXTRA_ARGS="--expert-placement-strategy round_robin"
```

### 6. `--enable-eplb` (기본 False) [소스확인]
Expert Parallelism Load Balancer — 런타임에 전문가 부하를 재배치.
`num_redundant_experts` 로 인기 전문가 복제. EP 불균형의 근본 해법이나
설정 복잡(window/step). EP 구성 성숙 후 시도.

### 7. `--compilation-config` cudagraph/컴파일 튜닝 [소스확인, 가설]
`cudagraph_mode`, `max_cudagraph_capture_size`, `compile_sizes` 조정.
DP4 에서 컴파일 직렬화로 기동 10분+ 걸린 것도 이쪽 — 기동 시간 단축 여지.
성능보다 운영 개선 성격.

## 우선순위 요약 (성능 기대 × 리스크)

| 순위 | 옵션 | 기대 | 근거 강도 |
|---|---|---|---|
| 1 | DCP (`--decode-context-parallel-size`) | **저conc 손실 없이 KV↑** — DP attention 상위호환 가능 | [소스확인] world size 안 늘림 |
| 2 | DBO (`--enable-dbo`) | 통신을 계산에 숨김 — EP 손실 상쇄 | [소스확인] 임계 조건 확인 |
| 3 | all2all deepep/flashinfer | EP all-to-all 직접 가속 | [소스확인] 커널 의존성 미확인 |
| 4 | `--no-scheduler-reserve-full-isl` | admission 공격적 | [소스확인] 저비용 |
| 5 | expert round_robin / EPLB | EP 부하균형 | [소스확인] EP 전용 |

## 실험 순서 제안

1. **DCP 단독** (dcp2, dcp4) — 가장 유망. TP=8 유지하며 KV 만 늘리는지 full sweep
2. **DBO** — TP8·EP1 위 + TP2·DP4·EP8 위 둘 다
3. DCP 가 되면 **DCP + DP 조합** 도 가능 (KV 를 두 축으로)
4. all2all 백엔드 — EP 구성이 승자로 남으면

각 실험은 `experiments.conf` 한 줄. 스크리닝은 `SWEEP=32,128,256` 로 단축,
승자만 full sweep.

## 안 되는 것으로 재확인된 것 (재실험 금지)
- NVFP4 (요청 제외)
- TP<8 + EP 없음 (OOM), mnbt 상향 (무효), disable-custom-all-reduce (역방향)
